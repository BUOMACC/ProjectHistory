## 1. Skill
### 1.1 개요
<hr>
<img src="https://github.com/BUOMACC/ProjectHistory/blob/main/Images/HA_Skill_01.png" width="100%" height="100%"/>

  
전투를 진행하면서 사용되는 공격이나 구르기, 그리고 Q / E를 눌러 발동시키는 연계 기술들의 사용을 관리하는 시스템입니다.  
플레이어가 스킬을 사용할 수 있도록 스킬 객체를 관리하고 서버와의 일관성을 유지하며 Cost / Cooldown에 대한 처리를 담당합니다.
<br/>
<br/>

### 1.2 기존 시스템의 문제
<hr>

이전 프로젝트(Hunter's Arena : Legends, HA:L)에서는 각 캐릭터별로 고유한 스킬을 가질 수 있는 환경이었기 때문에  
스킬을 단일 데이터로 관리하는 방식으로 무리가 없었습니다.    
<br>
하지만 캐릭터와 관계없이 장착한 무기에 따라 변화되어야 하는 스킬이 있는가 하면, 유저가 직접 스킬을 연결해 사용하는 방식도 필요하게 되었습니다.  
> ex) 유저는 A->B->C로 장착하여 사용할 수도, B->A->C로 장착하여 사용할 수도 있다.

`기본 공격1 - (검)` 그리고 `기본 공격1 - (창)`은 모두 동일한 하나의 `기본 공격1`로 취급되어야 했고, 자원 소모 역시 동일하게 적용되어야 했습니다.  
<br>
그 밖에도 `기본 공격1`이라는 하나의 스킬 아이콘으로 UI에 표시될 필요도 있습니다.  

이제 기존 시스템이 가진 문제점은 아래와 같았습니다.  

- `기본 공격1`은 모두 동일한 자원이 소모되도록 해야 하지만, 기존 시스템으로 유지할 경우 검과 창의 데이터를 모두 동일하게 변경해야 합니다.  
  이는 무기가 추가됨에 따라 수정해야 하는 작업이 점점 많아지는 번거로운 유지보수 문제가 있을 수 있습니다.
  <br>
- 쿨타임을 적용하는 스킬의 경우 `찌르기 스킬`에 해당하는 모든 무기에 대해 쿨타임을 직접 적용해야 합니다.  
  그렇지 않으면 무기를 스왑하고 다른 무기로 찌르기 스킬을 재사용할 수 있게 됩니다.
  <br>
- `찌르기 스킬` 이후 `올려베기 스킬`로 연결되어 사용하고 싶은데 두 스킬을 연결할 방도가 없습니다.

### 1.3 개선 방안
<hr>

우선 사용하고자 하는 스킬 시스템에서 요구하는 기능을 크게 두 방식으로 정의했습니다.  
- 무기별로 나뉘어진 액션들을 포함하여 하나의 스킬로 취급할 수 있어야 한다.
- 무기별로 그룹화한 스킬들을 서로 연결하여 원하는 콤보를 구현할 수 있도록 해야 한다.


#### 무기별로 나뉘어진 액션들을 포함하여 하나의 스킬로 취급할 수 있어야 한다.
<hr>

세부적인 스킬 정보를 표시하는 `SkillData`와 이들을 묶는 `SkillGroupData`로 분리했습니다.  
* `SkillData` : 이 스킬이 어떤 무기에서 사용될 수 있는지 나타내거나, 공격 정보(데미지 등..)를 포함합니다. 그룹화의 최소 단위입니다.
* `SkillGroupData` : `SkillData`를 묶어 인게임에서 하나의 스킬로 표현되는 단위입니다. 자원 소모량 정보들을 포함하고 있습니다.  

`SkillGroupData` 정보는 기반으로 인게임에서 스킬 객체 인스턴스(`SkillObject`)로 관리됩니다.  

#### 무기별로 그룹화한 스킬들을 서로 연결하여 원하는 콤보를 구현할 수 있도록 해야 한다.
<hr>

스킬은 하나의 부모 스킬로만 이어지고 거슬러 올라가는 경우가 없기 때문에, 트리 구조가 가장 적합하다고 판단하고 적용했습니다.<br>
각 스킬 노드들은 `Input`과 함께 매핑하여 자식 노드로 연결되므로 언제든 다른 전투 행동에도 할당할 수 있도록 유연성을 제공했습니다.
<br/>

### 1.4 편의성
<hr>

시스템을 편하게 사용할 수 있도록 `SkillObject`를 엮은 로직을 모듈화한 객체를 정의했습니다.<br>
이 객체는 `ApplySkillTreeData( )` 함수로 적용시 일괄적으로 트리에 구성된 스킬들의 권한이 부여됩니다.<br><br>
편의성을 위한 객체가 필요했던 이유는 아래와 같습니다.
- `기본 공격1` -> `기본 공격2` 연결의 경우 변경할 수 없으며 이는 정적인 스킬 콤보이므로 일괄 적용하기 좋음
  <br>
- 무기들은 모두 동일한 순서의 공격을 가지므로, 미리 작업해둔 객체를 재사용하면 별다른 로직 구현이 필요 없다는 장점  

### 1.5 부정행위 방지
<hr>

시스템을 구현하며 유저의 경험을 유지하면서 최소한의 부정행위는 방지하고자 `Client-Side Prediction` 방식을 사용했습니다.  
`Client`는 우선적으로 자신에게 보여지고 있는 자원을 기반으로 스킬을 사용하고자 하지만, `Server`측에서도 자원을 확인하고 검증합니다.  
<br>
만약 잘못된 시도를 하는 경우 `Server`가 가진 자원 정보와 함께 `Client`에 통지하며, 이 값을 토대로 자원을 갱신하는 방식으로 부정행위를 방지합니다.  

### 1.6 결과
<hr>

- 개발 환경에서 객체를 재사용하거나, 함수 몇 번 호출하는 것으로 빠르게 스킬을 구성하고 테스트 가능해짐
- 유저 플레이 경험을 확보하면서도 최소한의 부정행위 방지
- 인게임 디버그 UI 및 치트 개발 → 스킬 데이터 튜닝 시간 단축

## 2. Character Stat
### 2.1 개요
<hr>

플레이어의 체력, 공격력과 같은 능력치(스텟)를 관리하고 아이템이나 버프 등 프로젝트의 전반적인 기능에 연동할 수 있는 시스템입니다.


### 2.2 기존 시스템의 문제
<hr>

기존에는 스텟의 종류마다 개별 변수를 선언하는 방식으로 관리되었으며 아래와 같은 문제가 있었습니다.  

첫 번째로, 스텟을 추가/삭제하기 위해 모든 로직을 확인해야 하는 번거로움이 있습니다. 
- Table로 캐릭터의 고유 스텟을 불러오는 과정
- 스텟 증가 요소에 의해 스텟 변화가 생기는 경우, 이를 계산하는 로직에 반영해야 함  
  
캐릭터의 기본 이동속도를 나타내는 `MoveSpeed` 정보가 추가되었다면 이를 정의하고 관련 로직에 모두 반영해야 합니다.  
또한, 휴먼에러의 가능성도 높을 뿐 아니라 정상적으로 동작하는 것처럼 보이기 때문에 버그를 추적하는 비용도 많이 소요됩니다.  

두 번째로, 원본 값을 유지하기 위해 별도의 변수를 관리해야 하는 문제도 있습니다.  
캐릭터가 아이템을 장착하기 전 고유한 `Health` 값을 사용하는 경우 새로운 변수를 선언해야 합니다.  

세 번째로, 계산 로직이 명확하지 않고 분산되어 있는 문제가 있었습니다.  
아이템이나 버프를 통한 스텟 계산을 위해 플레이어가 가진 모든 스텟 정보를 별도의 구조체로 제공하고  
각 시스템에서 제공받은 능력치 구조체(데이터)를 기반으로 하여 증가량을 반환하거나 즉시 계산하고 값을 덮어씌우기도 합니다.  

이런 방식은 계산 결과를 예측하기 어렵게 만들어 스텟 변화가 생기면 모든 스텟을 다시 불러오고 계산하는 비효율적인 방향이 되었습니다.  

### 2.3 개선 방안
<hr>

스텟값을 관리하기 위해 전용 컨테이너를 설계하였으며, 원본(`Base`), 합(`Flat`), 곱(`Per`)연산에 대응할 수 있도록 `int32`로 분리하여 관리하도록 구현했습니다.  
또한 `int` 및 `float` 타입을 모두 지원하기 위해 `Fraction` 요소를 추가했습니다.  

최종 스텟 값은 조회 시점에 컨테이너가 보유한 `Base`, `Flat`, `Per` 값을 공통 연산 로직으로 계산하여 반환되도록 구성했습니다.  
아울러 나한테만 필요한 정보인지 여부에 따라 `Replication Condition` 값을 적용하여 네트워크 복제 비용을 최소화했습니다.  

### 2.4 결과
<hr>

- 타 시스템에서 더 이상 스텟을 계산하는 로직을 포함하지 않아도 되므로 복잡도가 줄어들었습니다.  
  단순히 `Flat` 및 `Per` 값을 추가하는 것으로 쉽게 스텟 변화에 관여할 수 있게 됩니다.
- 연산 순서를 통합하여 관리하므로, 계산 결과가 명확해지고 변화가 생기면 변화한 스텟만 계산하면 됩니다.  
- 스텟 추가/삭제를 위해 연관된 광범위한 코드를 확인할 필요가 없습니다.  
  타입을 정의하고 엮기만 하면 추가/삭제가 가능하고, 어떤 시스템에서든 타입을 통해 스텟을 활용할 수 있습니다.  

### 2.5 개선사항
<hr>

- 곱연산 수치들이 모두 합산되어 적용된다는 점에서 곱연산의 연속 처리를 위해 별도의 스텟 변수를 새롭게 추가해야 했습니다.  
  아래와 같이 채널을 추가하는 방향으로 개선했으면 다방면에서 활용하기에 더 좋았을 것 같습니다.

- 계산결과를 미리 캐싱할 수 있는 옵션을 제공하여 조금이나마 성능을 올리는 방식을 고려해볼 수 있었을것 같습니다.

## 3. 의뢰(퀘스트)
### 3.1. 개요
<hr>

<img src="https://github.com/BUOMACC/ProjectHistory/blob/main/Images/HA_Quest_01.png" width="75%" height="75%"/> 

`Lobby`에서 다수의 퀘스트를 수락받고, `InGame`에서 특정 행동(납품 / 처치 / 탈출 등)을 통해 하위 목표를 달성하여 퀘스트를 완료하는 시스템입니다.  
퀘스트 진행도를 언제든 확인할 수 있으며 값들은 실시간으로 반영되어 보여집니다.  

`Lobby`에서는 `Game Server`와 통신하고 `InGame`에서는 `Dedicated Server`를 기반으로 동작합니다.

### 3.2 설계
<hr>

#### 데이터 구조
먼저, 퀘스트가 어떻게 진행되는지 타 게임 사례를 통해 확인하고 달성해야 하는 세부 목표 데이터 구조를 다음과 같이 정의했습니다.   
- 달성을 위해 필요한 행동 (Type)
- 클리어를 위한 횟수 (int)
- 목표 대상 (int)
> ex: `오크 몬스터 5회 처치`를 예시로 들면, `몬스터 처치`는 행동이고, `5회`는 클리어를 위한 횟수를 의미하며, `오크`는 목표 대상이다.

그리고 세부 목표들은 Quest로 단위로 묶어 관리됩니다.  


#### 목표 처리
목표에 부합하는 행동을 하게 되면 모든 대상에게 이벤트를 발생시켜 카운트를 증가시키도록 작업했습니다.  
행동 타입(Type), 횟수(int), 목표 대상을 함께 전달하여 진행중인 퀘스트에 부합한 이벤트인 경우 카운팅 처리합니다.  

당시에는 한 판에 플레이하는 최대 인원이 10명 이내였기 때문에 모든 대상에게 이벤트를 발생시켰는데  
플레이하는 인원이 많아지게 되면 부합한 행동에만 반응하도록, 이벤트 구독 방식으로 처리하여 개선했을 것 같습니다.  

#### 패킷 데이터 관리
`Lobby`에서는 `Game Server`로부터 패킷 데이터를 수신하여 클라이언트측 퀘스트 데이터 구조로 컨버팅하여 관리했습니다.  
서버팀과 클라이언트팀이 작업하는 기간이 각자 다르고, 서로 데이터 구조를 본인의 프레임워크에 맞게 작업할 수 있어 패킷 조율 비용이 줄어든다는 장점이 있습니다.  

게임을 플레이하며 실시간으로 퀘스트 진행도를 확인할 수 있어야 했기 때문에, 변환된 데이터는 `Replicate`되어 `Unreal Networking` 기반으로 동작합니다.  
플레이하면서 달성된 목표들은 게임 종료 시점에 다시 `Game Server`에 맞는 패킷으로 변환하여 전송됩니다.  
> 종료 시점에 처리하면, 패킷 전송 비용을 줄일 수 있으며 탈출 성공 여부에 따른 진행도 유지에 대한 처리도 가능해집니다.


### 3.3 발생한 문제
<hr>


#### Localization 문제
각 어순이 다른 나라에서 퀘스트 설명을 표기하기 위해 Text Format 방식을 사용하였습니다.  
`Type`을 기반으로 설명이 표시되기 때문에 이를 기준으로 Text Format을 구성하고 런타임에 퀘스트 데이터로 값을 치환하여 설명을 생성했습니다.   
- 한글: `{Target} {count} 처치`
- 영어: `Kill {count} {Target} Monsters`

이런 방식으로 언어별 어순 차이를 자연스럽게 지원할 수 있었으며 여러 언어에서 올바른 문장 구조로 표현할 수 있었습니다.  


#### 로컬 시간변경 대응
퀘스트에는 만료 시간이 존재하는 퀘스트가 있었기 때문에 퀘스트를 다시 갱신해야 하는 경우가 종종 있었습니다.  
서버와의 지속적인 핑퐁 작업으로 시간을 확인하는 방식은 서버측에 부하가 있을 수 있다고 답변을 들었기에 클라이언트에서 이를 처리해야 했습니다.  

이때 임의로 로컬 시간을 변경하면 강제로 갱신 패킷을 전송하거나 남은 시간이 정상적으로 표시되지 않는 문제가 있었습니다.  
이를 해결하기 위해 퀘스트 정보를 나타내는 패킷에 서버의 시간(UTC)을 추가했습니다.  

그런 다음, 클라이언트의 시간에서 받은 서버 시간만큼 제외하여 오차를 구하고 이를 반영한 시간을 계산하여 표기하는 방식으로 해결했습니다.  
> ex: `Server`의 시간은 17:00, `Client`의 시간은 18:30이면 01:30만큼의 오차가 발생한다. 퀘스트 만료가 22:00에 된다면 정상적인 상황은
      05:00 만큼 남아야 하나, 조작된 로컬 시간에 의해 03:30으로 표기된다. 이때 오차(01:30)를 반영하여 정상적인 시간으로 보여지도록 함

### 3.4 결과
<hr>

- 행동들을 세분화하여 세부 목표를 조합하는 방식으로 Quest를 빠르게 추가할 수 있었음
- 각 `Type`에 맞는 행동을 하면 이벤트를 발생하는 방식으로, `목표 대상`이나 `횟수`에 의존하지 않고 대응 가능  
  `오크` `해골` 등 목표 대상을 id 기반으로 하여 어떤 몬스터를 잡아야 하는지 처리하기 위해 별도의 코드 수정이 필요하지 않음
- 로컬 시간변경에 대응하여 비정상적인 동작을 방지
- 텍스트 포맷 기반의 Localization 대응하여 어떤 나라의 언어에서도 자연스럽게 보일 수 있도록 처리

## 4. 스포너 및 검증 툴
### 4.1 개요
<hr>

월드 내 배치되는 `Item`, `Container`, `Monster`를 스폰하는 시스템입니다.  

공통 스폰 로직과 생성 방식을 분리하여 다양한 스폰 방식을 유연하게 적용할 수 있도록 설계했으며, 에디터 단계에서 스폰 위치를 미리 시각적으로 확인할 수 있도록 제작했습니다.  

### 4.2 접근 및 설계
<hr>

스포너 시스템은 공통 기능과 개별 생성 로직을 분리하기 위해 베이스 클래스 중심으로 설계했습니다.  

베이스 클래스에서는 스폰 주기 관리, 활성화 여부, 스폰 위치 계산 등 모든 스포너가 공통적으로 사용하는 기능을 담당하며, 실제 어떤 객체를 생성할지는 파생 클래스에서 결정하도록 구성했습니다.  

이를 위해 `GetMonsterClass()`와 같은 함수를 재정의 가능한 형태로 제공하여 `Item`, `Container`, `Monster` 스포너 각자의 생성 대상을 반환하도록 구현했습니다.  

이런 방식을 선택한 이유는 테스트 과정에서 생성 방식을 다양하게 테스트해보기 위해서였습니다.  
`Editor`에서 테스트를 위해서는 스폰대상 클래스를 명시적으로 지정해야 했고, 그 밖에도 테스트 과정에서 스폰 방식이 변경되는 경우가 많을 것이라고 판단했기 때문입니다.  

이를 통해 공통 로직의 중복 구현을 방지하고, 새로운 스포너 타입 추가 시 기존 코드 수정을 최소화하여 확장만으로 대응할 수 있도록 설계했습니다.  

또한, 바닥에 스폰될 수 있도록 GroundTrace를 처리하고 `ChildActorComponent`를 활용해 어디에 배치될지 미리 `Editor`에서 확인할 수 있도록 하여 시작-종료를 반복하는 번거로움을 줄였습니다.  

### 4.3 문제점 및 개선 방안
<hr>

수백개의 스폰 데이터와 레벨 내 배치된 스포너의 개수가 많아지면서 잘못된 데이터를 기입하는 휴먼에러가 종종 발생했습니다.  
최소한의 검증 장치로 런타임에 스포너가 동작하는 시점에 로그를 추가하긴 했으나, 로그를 확인하지 못하고 넘어가는 경우도 종종 있었습니다.  

`Editor`내에서 수정하거나 내부 테스트를 위해 빌드하게 된 경우, 뒤늦게 발생한 문제를 파악하고 수정 -> 빌드하는 과정이 최소 30분에서 길게는 1시간 넘게 시간이 소요되기도 했습니다.  

이런 불필요한 비용을 최소화하고자 잘못된 데이터를 검출해낼 수 있도록 `Editor Utility Widget`을 활용하여 검증 툴을 개발하여    
입력한 데이터가 기획적인 데이터 규칙에 어긋나거나, 누락하는 등 상황들을 조건 객체로 정의하여 사전에 잘못된 데이터를 미리 검출해낼 수 있었습니다.  

그밖에도, 새로운 검증 규칙이 필요하게 되면 기획자가 내부 코드를 수정할 필요 없이 새로운 규칙 객체만 추가하는 방식으로 쉽게 확장할수도 있었습니다.  

결과적으로 잘못된 데이터로 인해 다시 빌드하는 경우가 거의 없었으며, 에디터 내에서도 5분 이내로 빠르게 검출해 수정할 수 있게 되었습니다.   


### 4.4 결과
<hr>

- 공통 로직을 베이스 클래스로 통합하여 중복 구현 제거
- 새로운 스포너 타입 추가 시 확장만으로 대응할 수 있는 구조로 설계
- 오류 발생 시 5분 이내로 원인을 확인하고 수정할 수 있도록 휴먼에러 검출 시간 개선
- 잘못된 데이터 기입으로 인한 재빌드 빈도 비용을 줄임

## 5. Blueprint -> C++ 포팅
### 5.1 발생한 문제
<hr>

프로젝트를 진행하면서 `Blueprint Editor`를 열거나 수정, 컴파일하는 과정에서 최소 1분 이상의 지연이 발생했습니다.  

특히 로직을 수정하고 작업 중에도 매번 로딩과 컴파일을 기다려야 했기 때문에 개발 효율이 크게 저하되었으며, 특정 `Blueprint`의 경우 `Blueprint Editor`를 여는 데만 5분 이상이 소요되기도 했습니다.

### 5.2 원인 분석
<hr>

핵심 시스템은 `C++`로 구현되어 있었지만, 실제 게임 로직의 상당 부분이 `Blueprint` 파생 클래스에 작성되어 있었습니다.

또한 `Blueprint` 내부에서 다른 `Blueprint` 클래스를 직접 `Cast`하거나, 변수 및 함수 파라미터로 `Blueprint` 클래스를 참조하는 경우가 많아 에셋 간 참조 관계가 복잡하게 얽혀 있었습니다.

이로 인해 하나의 `Blueprint`를 로드할 때 해당 `Blueprint`가 참조하는 `Blueprint`와 `Asset`이 연쇄적으로 로드되었고, 일부 `Blueprint`는 순환 참조까지 포함하고 있어 단순한 클래스임에도 불구하고 수백 개의 관련 에셋이 함께 로드되며 지연되는 문제가 발생했습니다.

또한 Blueprint는 컴파일 시점에 `BlueprintGeneratedClass`를 생성하기 때문에, 하나의 `Blueprint`를 컴파일할 때 참조 중인 다른 `Blueprint`들의 로드 및 컴파일 과정이 연쇄적으로 발생하여 작업 시간이 더욱 증가했습니다.


### 5.3 개선 방안
<hr>

초기에는 `Cast`로 인한 참조 의존성을 줄이기 위해 `Interface` 기반 호출을 고려했습니다.

실제로 일부 참조 관계를 `Interface`로 대체하여 `Blueprint` 참조를 제거할 수 있었지만, 클래스와 1:1로 대응되는 `Interface`가 증가하며 아래와 같은 문제가 발생했습니다.
- `Interface`의 의미를 잃음 -> 재사용 불가, 의미없는 추상화
- 디버깅시 실제 구현부가 어딘지 실행 흐름을 추적하기 어려움
- 불필요하게 `Interface`의 수가 많아짐
- 수정이 필요한 경우 `Interface` 및 `Class` 둘 다 수정해야 함

따라서 단순히 `Interface`를 사용해 해결하고자 하는 방식보다 의존성의 근본 원인을 제거하는 것이 중요하다고 판단했습니다.

이후 `Blueprint`에 작성된 핵심 로직을 `C++`로 이전하고, `Blueprint`가 구체 클래스 대신 `Native` 클래스를 참조하도록 구조를 변경해 나갔습니다.

또한 `CoreRedirect` 기능을 활용하여 기존 데이터와 참조를 이전했습니다.

그 밖에도, 뒤늦게 로드되어도 상관없는 에셋들을 `SoftReference`를 이용해 참조 관계를 관리했습니다.


### 5.4 결과
<hr>

- `Blueprint` 클래스간 의존성을 줄이고 `Native` 클래스 중심으로 참조하도록 개선하여 에셋 로드 범위를 최소화했습니다.
- 순환 참조 및 연쇄 컴파일시 발생하는 문제를 완화하여 `Blueprint` 수정 시 발생하던 긴 대기 시간을 50% 이상 줄이고 개발 생산성을 향상시켰습니다.

## 6. 재접속
### 6.1 개요
<hr>

플레이어가 게임 진행 중 연결이 끊어진 경우에도 기존 진행 상태를 유지한채 다시 플레이할 수 있도록 재접속 시스템을 구현했습니다.	

이를 위해 언리얼 엔진의 접속 종료 및 재접속 처리 과정을 분석했으며, `PlayerController`, `Pawn`, `PlayerState`의 생명주기를 파악하고 세션 종료 전 재접속 시 기존 캐릭터와 데이터를 그대로 이어받도록 설계했습니다.	

### 6.2 접근 및 설계
<hr>

재접속 시스템 구현을 위해 우선적으로 해결해 나가야 하는 기능들을 나열했습니다.  
- `PlayerController`가 `Destroy`된 경우, `Pawn`도 함께 `Desotry`되는 현상
- 접속 종료 후에도 `PlayerState`의 데이터 유지를 위한 처리
- 다시 접속한 경우, `PlayerState`와 `Pawn`을 연결하는 처리
- 나간 상태에서 세션의 진행 처리

이런 기능들을 구현하기 위해 `Unral Engine`의 프레임워크 코드를 분석했습니다.  


#### PlayerController가 Destroy된 경우, Pawn도 함께 Desotry되는 현상
<hr>

플레이어가 퇴장한 상태에서 다른 사람에게 공격받을 수 있어야 하고 `Pawn`이 가진 정보를 그대로 유지한 채 다시 시작할 수 있어야 하기 때문에 `Pawn`을 다시 리스폰하는 방식보다 유지하는 방식이 합리적이라고 판단했습니다.  

이를 해결하고자 `APlayerController::Destroyed()` 함수를 오버라이딩 하여 `Pawn`이 `Destroy`되지 않는 방향으로 수정했습니다.


#### 접속 종료 후에도 PlayerState의 데이터 유지를 위한 처리  
<hr>

`PlayerState`에서 플레이 데이터를 가지고 있었기 때문에 종료한 뒤에도 `PlayerState`를 유지하고 있어야 했습니다.  
`Unreal Engine`은 비활성화된 플레이어를 기존의 `PlayerState`를 복제한 `InactivePlayerState` 객체로 유지하고 기존의 `PlayerState`는 `Destroy` 됩니다.  

하지만, 복제하는 함수 `APlayerState::Duplicate()`는 단순히 새로운 `PlayerState`를 생성하고 수동으로 값을 복사(`APlayerState::CopyProperties()`)하는 과정에 불과했습니다.  

``` C++
void APlayerState::CopyProperties(APlayerState* PlayerState)
{
	PlayerState->SetScore(GetScore());
	PlayerState->SetCompressedPing(GetCompressedPing());
	PlayerState->ExactPing = ExactPing;
	PlayerState->SetPlayerId(GetPlayerId());
	PlayerState->SetUniqueId(GetUniqueId());
	PlayerState->SetPlayerNameInternal(GetPlayerName());
	PlayerState->SetStartTime(GetStartTime());
	PlayerState->SavedNetworkAddress = SavedNetworkAddress;
}
```

이런 방식은 기존의 데이터를 유지하기 위해 데이터를 모두 `APlayerState::CopyProperties()` 함수를 통해 추가해줘야 하는 번거로움이 있습니다.  

그래서 기존의 `PlayerState`를 유지하고 `InactivePlayerState`로 사용할 수 있도록 `GameMode` 코드를 개선했습니다.


#### 다시 접속한 경우, PlayerState와 Pawn을 연결하는 처리  
<hr>

플레이어가 다시 세션으로 복귀할 때의 시점 `AGameMode::PostLogin()` -> `FindInactivePlayer()`에서 고유 Id를 활용해 매칭했습니다.  
`PlayerState`를 매칭시킨 이후에는 플레이어가 시작되는 시점 `HandleStartingNewPlayer()`에는 접속종료된 `Pawn`을 찾아 캐싱한 고유 Id로 매칭하여 빙의합니다.  


### 6.3 발생한 문제
<hr>

첫 번째로, `PlayerState`가 `Inactive`된 상태에서 유지되는 시간이 짧아 재접속 전 파괴될 우려가 있었습니다.  
→ `InactivePlayerStateLifeSpan` 값이 `300.f`로 설정되어 있었으므로, 이 값을 조절하여 세션 종료까지 유지되도록 했습니다.  

두 번째로, 플레이어가 접속을 종료하면 `Pawn`은 어떤 상황에서도 밀려나지 않던 문제가 있었습니다.  
`Pawn`은 `Controller`을 잃은 상태로 `CharacterMovementComponent` 내부에서 `Acceleration` 및 `Velocity` 값이 항상 초기화되어 시뮬레이션 되지 않았습니다. 
→ 내부값 `bRunPhysicsWithNoController`을 활성화 시켜 문제를 해결했습니다.  

세 번째로, 재접속시 일부 데이터가 동기화되지 않았습니다.  
일부 시스템은 `Replicate` 기반으로 작업되어 정상적으로 데이터가 동기화되고 있었지만, 복잡한 데이터의 사용 등으로 `RPC`를 통해 동기화를 진행한 시스템은 다시 동기화하는 작업이 필요했습니다.  

→ 재접속시 호출되도록 이벤트 `OnReconnect()` 함수를 추가하여 데이터를 다시 동기화하도록 처리했습니다.  


### 6.4 결과
<hr>

- 플레이어가 접속 종료 후 재접속 하더라도 이전 정보를 유지한 채 게임을 이어 진행할 수 있도록 구현했습니다.
- `InactivePlayerState` 관리 방식을 파악하여 불필요한 복제 비용을 줄였습니다.
